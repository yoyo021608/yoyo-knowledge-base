# 架构文档

## 1. 架构目标

- 让知识收录、检索、问答和来源追溯各自有清晰边界。
- 让 React 前端、FastAPI 后端和基础设施彼此分离。
- 让模块可以通过接口联动，但不能把别的模块业务复制到自己目录。
- 让文档版本、来源快照、会话引用和回答结果形成可追溯链路。
- 让一个功能能够定位到一个领域模块、一个 Issue 和一个 Pull Request。

本文说明模块怎么分、边界在哪、目录怎么放，以及模块之间怎么联动。

## 3. 模块职责与边界

后端领域模块：

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| 账户（users） | 注册、登录、修改密码、忘记密码、注销和当前用户身份 | 不判断某条资料或某个会话该不该被访问 |
| 文档（documents） | 资料的收录、组织、归档、删除、版本、来源、索引、检索和导出 | 不生成回答，不做检索编排 |
| 编排（agent） | 一次问答的编排：问题改写、检索编排、证据判断、回答生成和运行控制 | 不拥有文档、版本和索引数据 |
| 会话（sessions） | 会话、消息和回答引用的保存与回放 | 不负责过程事件、取消、断线恢复和回答策略 |
| 基础设施（infra） | 数据库、缓存、文件存储、后台任务和模型配置 | 不做任何业务判断 |

编排（agent）内部还有三个不单独成模块、只作为子包存在的部分。它们的边界最容易写错，所以单独说明：

- `agent/rag`：负责问题改写、检索计划、上下文组装、证据判断和多步编排，产出检索计划、上下文和证据结论；不直接访问文档数据库，不拥有索引。
- `agent/tools`：负责工具定义、参数、权限和结果适配，是编排调用文档能力的适配层；不实现文档的切分、版本和检索算法。
- `agent/prompts`：集中存放系统提示和各类任务提示，提示词不散落在代码里。

前端包：

- `apps/web`：Web 路由、页面入口、Provider、前端环境变量和平台装配。
- `packages/core`：无头业务能力、领域类型、API 客户端和纯逻辑；不依赖 React、DOM、Next 或 `process.env`。
- `packages/ui`：无业务 UI、通用组件、样式和交互基础设施；不依赖 `core`。
- `packages/views`：按业务域把 `core` 与 `ui` 组合为页面视图；不读取平台环境变量，不直接依赖路由框架。

## 4. 模块联动与架构约束

### 分层与依赖方向

前端依赖方向固定为：

~~~text
apps/web → packages/views → packages/core
                    ↓
                packages/ui
~~~

`packages/ui` 不反向依赖 `packages/core`。未来如果增加 CLI，只允许依赖 `packages/core`，不能依赖 React 页面和路由层。

后端统一入口是 `server/app/main.py`，依赖方向为：`app/api` 调用领域模块，领域模块调用 `app/infra` 或显式 Port，`app/infra` 不反向依赖业务模块。各层职责：

- `app/main.py`：启动、Router 组装、依赖注入和生命周期，只做装配。
- `app/config.py`：环境变量、模型名、索引与缓存参数；放在顶层，各层直接读取。
- `app/api`：HTTP 路由、请求/响应 DTO、参数校验、认证依赖和响应组装。
- `app/users`、`app/documents`、`app/agent`、`app/sessions`：按领域拆分的业务包，见第 3 节；`app/agent` 下带 `rag` 和 `tools` 两个子包。
- `app/infra`：数据库连接、缓存、后台任务、文件存储、向量库访问和模型 SDK 客户端。

### 领域包内部约定

每个领域包内部按同一套文件约定组织，以 documents 为例：

~~~text
app/documents/
├── models.py     # 该领域拥有的数据模型
├── schemas.py    # 对外的请求/响应结构
├── service.py    # 该领域的业务逻辑
└── ports.py      # 允许其他模块调用的接口
~~~

领域数据模型留在各自领域包内，不建 `app/models.py`、`app/schemas.py` 这类公共横切文件。

### 模块联动规则

- agent 调用 documents 的能力，不复制 documents 实现。
- 跨模块联动使用显式接口、Port 或 DTO，不通过直接修改别的模块内部数据完成。
- 检索的「怎么查」（检索计划、要不要再查一次）属于编排；检索的「怎么算」（切分、索引、检索算法和结果融合）属于文档。
- 融合排序的权重由编排给出，文档按参数执行；文档不自行决定检索策略。
- 多步检索由编排决定是否再查，每一次查询仍由文档执行；文档不自行循环重查。
- 回答引用由编排产生、由会话保存，引用始终绑定具体文档版本或来源快照。
- 运行过程事件、取消、继续和断线恢复属于编排，不放进会话，细节见 `docs/modules/agent.md`。
- 删除会话时，对应的运行记录由编排提供按会话清理的入口，会话不直接操作编排的数据。

### 架构约束

- `api` 是唯一的 HTTP 暴露层，领域业务不能全部写入 `app/api`。
- 领域模块提供内部业务方法和 Port，不直接依赖 FastAPI 路由对象。
- 对外请求/响应 DTO 在 `api` 或对应领域的 schema 中定义，不能把 ORM 对象直接作为公开响应。
- agent 只能通过 `DocumentSearchPort` 等显式接口调用文档能力。
- 索引、切片和向量数据由 documents 独占；agent 不直接连接向量库。
- 数据库、Redis、文件存储、向量库和模型 SDK 客户端只能由 `app/infra` 创建；领域模块不自己新建外部客户端。
- 不使用通用 `utils`、`services` 或 `repository` 包承载所有业务。
- 不创建没有实际职责的通用 `server/app/ai` 或深层 LLM Provider 包装。
- 模型调用直接使用官方 SDK 或兼容 SDK。

## 5. 关键取舍

- **检索为什么是「向量 + 全文」两条路再融合，而不是只做向量**：只做向量，对型号、错误码这类精确词不敏感；只做关键词，对同义表达不敏感。个人知识库里「记得意思不记得原词」和「记得一个精确编号」两种场景都常见，所以两条路都要，再按权重融合。
- **RAG 为什么是 agent 的子包，而不是独立模块**：问题改写、检索计划和证据判断，都由「这一轮问答该怎么问」决定，脱离 agent 的运行编排就没有意义；独立成模块只会逼着两边互相调用。文档的切分、索引和检索算法仍然归 documents。
- **回答引用为什么绑到文档版本和来源快照，而不是绑到文档本身**：文档会被改写，来源网页会失效。只绑文档，回看旧回答时看到的是「现在」的内容，等于伪证；绑版本和快照，历史回答才能还原成当时的样子。
- **过程事件为什么先落库再推送，而不是只走内存**：流式事件只是通知，一断线就丢。一次问答动辄几十秒，断线并不罕见。事件带序号落库后，重连可以从任意位置续上，前端也不必自己维护「已经收到哪些」的复杂状态。
- **LLM 为什么直接调官方 SDK，不封一层 Provider**：模型调用本身就是一次 HTTP 请求，再包一层只是多一个要维护、要测试、要跟着 SDK 升级的中间层。真正需要隔离的是密钥、base_url 和模型名这类配置，那是 infra 的职责。
- **为什么不设全局 `utils` / `services` / `repository` 包**：这类包一开，任何不知道放哪的逻辑都会往里塞，最后变成谁都不敢改、模块边界也失效的垃圾场。强相关的逻辑留在各自模块；确实要跨模块复用的能力，由**拥有它的模块**通过显式接口导出，例如 documents 导出 `DocumentSearchPort`，不另开通用包。

## 6. 模块联动示例

RAG 是 Agent 的子能力：RAG 负责「如何检索和使用知识」，documents 负责「知识如何保存、切分、索引和被检索」。一次问答的调用链是：

~~~text
用户问题
  ↓
agent/rag：问题改写与检索计划
  ↓
agent/tools：工具和参数适配
  ↓
DocumentSearchPort
  ↓
documents：全文、向量和混合检索
  ↓
agent/rag：上下文组装与证据判断
  ↓
Agent：调用模型 SDK 生成回答
  ↓
sessions：保存消息与引用
~~~

Agent 决定是否调用工具；工具只负责参数和结果适配；文档内容、切分、版本、索引和检索数据仍归 documents。

主线：一份资料从进来到被用出去。

小林注册账号并登录后，把一篇网页文章和一个 Markdown 笔记录入知识库，打上「备份」「数据库」两个标签，归入「运维」专题。一周后他遇到问题，新建一个会话提问。系统先把问题改写成适合检索的说法，同时走向量检索和全文检索两条路，从文档那里取回候选片段，融合排序后筛出最相关的几条。

第一次检索回来的片段不足以支撑回答，系统没有直接编答案，而是自己换了一组关键词又查了一遍；这次证据足够，于是生成回答，并在每条结论后面标出出处。他把这条会话改名为「备份方案调研」。

后来他发现那篇笔记写错了，改完保存，索引自动刷新。再问同一类问题时，回答依据已经是最新版本；而一周前那条旧回答里的引用，仍然指向当时的那一版。

支线：分类和运行过程的变化。

他把「运维」专题改名为「基础设施」，又删掉了一条录错的资料；那条资料此前被引用过，旧回答里的引用依然能打开当时的快照。

提问过程中如果检索很慢，小林能看到系统正在进行到哪一步；如果发现问错了，他可以取消；如果中途断网，重新打开页面后，之前已经产生的过程会按顺序补回来。

## 7. 关键设计问答

### 知识怎么建模和组织，为什么这样利于检索

资料以「文档 + 版本」建模：正文改动产生新版本，索引只跟最新版本，历史回答的引用绑当时那一版和来源快照。组织用专题、标签、关联三种可交叉的关系，而不是一棵目录树——一篇资料可以同时属于「运维」专题、带「数据库」标签、和另一篇资料关联。这些维度直接成为检索的过滤条件（`TopicID`、`Tag`），先缩小范围再算相关度，比全库算完再筛更准也更快。实现见 `docs/modules/documents.md`。

### 检索链路怎么设计，不准时怎么办

链路是：问题改写 → 检索计划 → 关键词 / 全文 / 向量三路召回 → 融合排序 → 证据判断。「怎么算」（切分、索引、召回、融合）在 documents；「怎么查、还要不要再查」在 agent。判断由 `RAGPipeline.AssessEvidence` 给出，不够时 `PlanNextRetrieval` 换一组参数再查一次；仍不够就返回明确的「证据不足」，不编答案。实现见 `docs/modules/agent.md`。

### agent / 工作流怎么处理一步答不好的问题

不引入多 Agent 工作流：单用户知识库的问答链路很短，多一层编排只会让行为更难预测。一次答不好通常是「一次检索召回不够」，处理方式是让编排换一组查询参数再查一次，而不是把问题推回给用户重问；仍然不足就走 `GenerateInsufficientEvidence` 返回明确结果。多步检索由编排决定，每次查询仍由 documents 执行。

### 怎么评估检索质量

先做运行中自然产生、可核查的信号，不做离线评测集和打分：`EvidenceDecision` 里的命中数量 `HitCount`、是否充足 `Sufficient`，以及二次检索是否被触发、证据不足的占比。这些随每次 Run 落库，可以按会话或按时间回看。回答是否被采纳、引用是否被点开属于产品侧信号，不在这里统计。
