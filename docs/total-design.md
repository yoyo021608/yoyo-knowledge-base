# 产品需求文档

## 一、产品形态

个人知识库管理系统，形态是 Web 应用：在浏览器里录入和整理资料，用一个问题把库里的知识问出来，并且能看清楚答案依据的是哪一条、哪一版资料。面向个人使用，每个账号独立管理自己的资料，不涉及多用户协作、公开分享和内容审核。

系统提供四种使用方式：快速问答用于查找单条知识；深度研究用于拆分复杂问题并汇总多份资料；文档对比用于比较不同文档或版本；学习模式用于根据知识点生成练习并记录掌握情况。四种方式共用知识库和引用机制，只由 Agent 选择不同的处理流程。

## 二、为什么需要它

资料收录需要配套检索、关联和来源验证能力。个人资料管理存在三个问题：

1. 资料分散：资料散落在浏览器收藏夹、笔记软件、本地文件夹和聊天记录里，各管各的。
2. 关联不足：单条资料能翻出来，但它和相关的其它资料之间没有联系，线索会断。
3. 依据不明：直接问模型能得到通顺的回答，但无法确认它是不是基于自己的资料。

对应三个目标：

- 收录：任何形态的资料都能进得来，并且进得来之后能被组织。
- 找回：凭模糊印象也能定位到具体内容。
- 可信：回答必须给出出处；未找到足够依据时明确说明证据不足，不断言库中绝对不存在相关内容。

## 三、功能清单

以下按业务模块和功能类别列出产品功能，MVP 范围以 docs/mvp.md 为准。基础设施不提供面向用户的功能，因此不出现在本节。

#### 账户（users）

| 功能 | 为什么要做 | 什么场景会用到 |
| --- | --- | --- |
| 用户注册 | 知识库是私有资产，资料必须归属于具体的人，否则无法隔离 | 第一次使用系统 |
| 用户登录 | 换设备或隔一段时间回来，需要进入自己的知识库 | 换电脑、重开浏览器 |
| 修改密码 | 密码可能泄露或想主动更换，走忘记密码流程是绕远路 | 主动更换密码 |
| 忘记密码 | 长期使用的账号必须有找回路径，否则资料会被永久锁死 | 忘记密码 |
| 注销 | 共用设备上必须能主动退出，避免资料被下一个人看到 | 在公共电脑上用完后 |

### 文档（documents）

#### 收录

| 功能 | 为什么要做 | 什么场景会用到 |
| --- | --- | --- |
| 单个录入 | 知识来源形态多样，普通笔记、Markdown、网页链接、上传文件需要统一收录入口 | 看到一篇好文章想存下来 |
| 批量录入 | 已有大量旧资料时逐条录入太慢，增加迁移成本 | 从旧笔记软件搬家 |
| 批量录入进度 | 批量导入耗时长，用户需要知道进行到哪一步，而不是对着转圈等 | 导入 200 个文件时查看进度 |
| 批量失败条目重试 | 批量导入必然有部分失败，失败条目需要独立重试 | 导入 200 个文件，其中 3 个格式不支持 |

#### 展示与维护

| 功能 | 为什么要做 | 什么场景会用到 |
| --- | --- | --- |
| 文档列表与筛选 | 资料数量增加时，需要通过列表和筛选定位内容 | 查看某个专题下的全部资料 |
| 文档详情 | 需要看到正文和来源，而不是只有一个标题 | 点开一篇资料确认内容 |
| 文档编辑与改写 | 知识会过时、会写错，不能修订的资料没有长期价值 | 补充或修正一篇笔记 |
| 改写后自动刷新索引 | 改了内容而索引不同步，问答就会引用旧内容，造成答案与资料内容不一致 | 改完文档后马上提问 |
| 版本保留 | 历史回答引用的可能是旧内容，不保留版本就无法回溯当时的依据 | 回看半年前的引用来源 |
| 归档与恢复 | 有些资料暂时用不上但不想删除，需要能收起来，也需要能再放出来 | 整理已过时的项目资料 |
| 删除文档 | 清除正文和历史版本；已有回答仅保留引用摘录与来源信息，并提示原文已删除 | 删掉一条录错的内容 |

#### 组织

| 功能 | 为什么要做 | 什么场景会用到 |
| --- | --- | --- |
| 专题（含改名与删除） | 单一文件夹结构无法同时表达多个组织维度，而且分类本身会变，必须能改名和撤销 | 把「运维」专题改成「基础设施」 |
| 标签（含改名与删除） | 同一篇资料往往跨多个主题，需要交叉标记；标签用久了也会过时 | 给一篇资料同时打上「性能」和「数据库」 |
| 收藏 | 常用资料需要快速入口，否则每次都要重新搜 | 快速打开高频使用的资料 |
| 文档关联（建立与解除） | 知识之间有关系，孤立存放会让线索断掉；关系判断错了也要能撤销 | 把「问题记录」和「解决方案」关联起来 |

#### 来源追溯

| 功能 | 为什么要做 | 什么场景会用到 |
| --- | --- | --- |
| 来源记录与来源快照 | 网页会失效、内容会被改，不保存快照就无法验证当初的依据 | 引用一篇后来被删除的文章 |

#### 检索

| 功能 | 为什么要做 | 什么场景会用到 |
| --- | --- | --- |
| 关键词检索 | 用户常常记得一个精确的词或编号，这是最快的定位方式 | 搜一个产品型号或错误码 |
| 全文检索 | 需要在正文里找到包含某段表述的资料 | 搜「怎么回滚」 |
| 向量检索 | 用户经常只记得意思、不记得原词，需要按语义找回 | 搜「备份方案」，原文写的是「数据副本」 |
| 混合检索 | 单靠向量对精确词和数字不敏感，单靠关键词对同义表达不敏感，两者互补 | 同一句话里既要精确匹配又要语义召回 |

#### 导出

| 功能 | 为什么要做 | 什么场景会用到 |
| --- | --- | --- |
| 导出资料 | 资料是用户自己的资产，必须能带走，便于迁移和备份 | 换工具或做本地备份 |

### 编排（agent）

#### 检索编排

| 功能 | 为什么要做 | 什么场景会用到 |
| --- | --- | --- |
| 多步检索 | 一次检索可能缺少充分证据，需要自动补充查询 | 第一次没搜到相关片段，系统自己换一种查询再查一次 |

#### 问答

| 功能 | 为什么要做 | 什么场景会用到 |
| --- | --- | --- |
| 基于知识库问答 | 检索结果需要整合为具有明确依据的回答 | 直接问「我上次是怎么解决这个问题的」 |
| 回答引用与来源追溯 | 无法验证来源的回答等同于模型幻觉，失去知识库的意义 | 核对答案出自哪篇文档哪一版 |
| 证据不足时明确返回 | 知识库里没有的内容必须如实说明，不能编造 | 问一个知识库里完全没有记录的问题 |

#### 运行控制

| 功能 | 为什么要做 | 什么场景会用到 |
| --- | --- | --- |
| 过程事件 | 模型调用耗时长，用户需要看到系统在做什么，而不是干等 | 检索和生成过程中显示进度 |
| 取消 | 发现问错了或等太久，需要能中止 | 提问后立刻想改问题 |
| 继续 | 中断后复用已完成步骤；生成中断时重新生成该轮，中断前的部分输出标记为失效 | 服务重启后继续尚未完成的回答 |
| 断线恢复 | 网络中断后重新进入，已产生的过程不能丢 | 手机切网络后回到页面 |

### 会话（sessions）

| 功能 | 为什么要做 | 什么场景会用到 |
| --- | --- | --- |
| 会话历史 | 多轮问答需要上下文，也需要事后回看结论 | 翻看之前问过的问题 |
| 会话改名 | 会话多了以后默认名称无法区分，需要自己命名 | 把「新会话」改成「备份方案调研」 |
| 引用回放 | 重新打开历史回答时，引用要能一起恢复 | 回看半年前的一条回答及其出处 |
| 删除会话 | 会话攒多了会干扰查找，试错性质的记录需要能清掉 | 清理一串问错的会话 |

模块的职责、目录归属和依赖方向见 docs/architecture.md，每个模块的内部设计见 docs/modules/。

下面说明用户能看到的功能结果，以及一次功能由哪些模块完成。模块内部的详细接口仍放在 `docs/modules/`，这里只保留产品层面的说明。

| 知识更新 | 编辑或重新导入已有文档 | 创建新版本，刷新新版本索引，保留旧版本引用 | 当前版本可检索，历史回答仍可回溯 | documents |
| 运行恢复 | 刷新页面或重新连接中断任务 | 读取 Run 快照和事件，复用已完成步骤 | 继续任务或看到明确的终止状态 | agent + infra |

## 五、核心数据流

文档录入先建立文档和版本，再保存来源快照并异步刷新索引；索引任务绑定具体版本，只有最新版本完成索引后才进入可检索状态。文档修改不会覆盖旧版本，历史回答仍然可以定位当时使用的版本。

用户提问时，controller 先校验会话，sessions 提供历史上下文，agent 改写问题并决定关键词、全文、向量或混合检索的组合，再通过 `DocumentSearchPort` 请求 documents 返回符合归属、版本和索引状态的候选片段。agent 对候选片段进行融合、重排和证据判断，证据不足时只在预算内补查，仍不足则返回明确的证据不足状态；证据充分后再按 token 预算组装上下文并生成带引用的回答。

完整回答和引用由 sessions 原子保存，Agent 的 Run、事件和步骤快照单独保存。客户端断线后按照事件序号回放；服务重启后读取快照并复用已完成步骤，避免重复执行整轮问答。

详细流程见 `docs/flows/`：文档录入、文档更新、问答和运行恢复。

## 六、项目创新点

本项目的重点不是增加 CRUD 数量，而是处理知识库问答中容易被忽略的可靠性问题：

- **证据门槛**：回答前判断证据是否覆盖问题，证据不足时补查或明确拒答，避免把模型猜测当成知识库结论。
- **检索预算**：分别限制补查次数、检索时间、历史消息和证据片段的 token 预算，防止检索结果过多导致上下文失控。
- **版本感知引用**：引用同时绑定文档、版本、片段和来源快照，文档更新后仍能解释历史回答依据。
- **可恢复 Run**：把一次问答拆成可持久化步骤，断线或重启后复用已完成步骤，减少重复模型调用。
- **混合检索解释**：同时保留关键词、全文和向量命中信息，让用户知道资料为什么被召回。

这些设计分别借鉴了开源项目中已经验证过的做法：RAGFlow 的解析、切片和失败状态用于文档入库；NexusRAG 的混合检索、重排和页级引用用于问答；GraphRAG 的实体关系用于组织跨文档知识；LangGraph 的检查点用于恢复中断的研究任务；Ragas 和 Langfuse 的评估与追踪用于记录检索质量、耗时和 Token。项目只采用这些机制解决自身问题，不引入与当前范围无关的完整框架。
